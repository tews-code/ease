Feature todo
============

Planned features, in priority order. Higher priority than docs/cleanup.txt,
which holds small tidy-ups noticed along the way. Each item is split into
steps that each pass CI and can be committed on their own.

Tick with [x] when done, or delete the line.

[ ] Console input: fd 0 reads from a "console input" role, not a device.
    Model (QEMU mirrors the real hardware):
      - typing in konsole -> UART  ==  Pi Debug Probe serial -> RP2350 UART
      - typing in the QEMU window -> virtio keyboard  ==  SPI keyboard
    Both sources feed console input; READ and the shell only ever see fd 0.
    Design:
      - One wait queue owned by the console-input layer; every source calls
        "notify console input" after pushing (replaces RX_AVAIL and
        KEYS_PENDING as wait points; a thread can sleep on only one queue).
      - Each source keeps its own ring (UART RX bytes, keyboard KEYS); no
        merged ring, since SPSC allows one producer.
      - One lock over both consumers: wait_with_interruptible locks a single
        resource, so the console-input struct holds the UART reader AND the
        keyboard consumer. READ's predicate drains whichever has data.
      - Common format: bytes, special keys as ANSI escape sequences
        (ESC [ A for Up), which a terminal already sends over the UART.
      - Known limitation: simultaneous typing on both sources can interleave
        an escape sequence. One human types; note it, don't engineer it.
    Steps:
    [x] 1. READ syscall with console input backed by the UART only: rename
           the fd Entry/Kind to console input, READ has one arm, UART RX
           IRQ wakes the console-input queue. Error-path tests (bad fd,
           fd 1, bad/read-only buffer, zero length); blocking test needs a
           way to inject RX bytes.
    [x] 2. Retire GET_CHAR; move the echo user program to READ.
    [x] 3. Virtio keyboard as the second source, ASCII only: its consumer
           moves into the console-input struct, the decoder thread notifies
           console input.
    [x] 4. Special keys as escape sequences, by byte-pushing: the keyboard
           queue carries u8, and the Decoder pushes each key's bytes (one
           for a character, the xterm sequence for a navigation key) whole
           or not at all, checking free space first. No peek needed: a
           sequence may still split across READs (UART input can anyway),
           and vt_parse is a byte-at-a-time state machine that handles
           that. DecodedKey and ease-abi special_key removed; fixes the
           >0xFF special-key truncation.

[ ] User heap: a syscall that gives a process a fixed-size heap on
    request, and the ease-ulib #[global_allocator] over it. Design
    agreed 2026-10-28:
      - Explicit setup: the program calls a ulib setup function with
        the size it needs, at the start of main, before any allocation
        and before spawning threads. Common embedded no_std pattern
        (embedded-alloc, linked_list_allocator init); Linux's lazy
        malloc doesn't fit because it relies on the heap growing.
        Allocating before setup fails with a clear message.
      - Nothing at spawn: a program that never asks pays no memory and
        no PMP entry for a heap.
      - Syscall: kernel rounds the request up to a power of two,
        allocates a NAPOT block, adds Role::Heap to the process map,
        returns base and actual size. PMP is rebuilt from the map on
        every switch (stride.rs, to_pmp), so the caller sees it on
        return; setup before spawning threads means no sibling can be
        running with a stale PMP.
      - Second call: error (setup is once, so it's a bug).
      - Pool by size: small heaps from UserPd0 (fast SRAM, 512 B steps,
        threshold e.g. 64 KB), large from Psram (4 KB steps). Programs
        may get a say in the pool later if needed.
      - Limits: minimum 512 B (smallest Order, B512; the PD0 buddy
        itself goes to 16 B). Maximum 4 MB, for Doom. UserPd0 is only
        256 KB, shared with all user stacks, so 4 MB means Psram, and
        today's Psram buddy is exactly 4 MB (__user_heap_psram_size):
        Doom's heap would take the whole pool, leaving none for BufRW.
        Order stops at KB128, so needs sizes up to MB4. Option: grow the
        Psram buddy toward the 8 MB part (user .text sits right after
        the Psram heap today, linker ASSERT in memory-qemu.x, and could
        move).
      - No growth, no moving: without an MMU, pointers into the heap
        can't be fixed up after a memcpy. Growing in place (doubling
        into a free buddy) is possible later but not guaranteed;
        put aside. Out of memory = Rust alloc error = process dies.
      - Freed at process teardown with the map; the syscall undoes its
        own allocation if it fails partway.
      - Allocator: the existing linked-list allocator, as GlobalAlloc
        in ease-ulib, initialised empty and set up from the syscall's
        base/size. Its lock must be an atomic spinlock (U-mode can't
        disable interrupts; threads share the heap).
    Steps:
    [ ] 1. Kernel: the heap syscall (limits, pool choice, second-call
           error). Probe: ask for a heap, write it, check one past the
           end PMP-faults, check a second call errors.
    [ ] 2. ease-ulib: allocator as #[global_allocator] + setup function.
           Probe: set up a heap and use a Vec.

[ ] Move the shell's line_editor and vt_parse to user space, on a user
    heap instead of large stack buffers (LineEditor holds the line, the
    saved line and HISTORY_SIZE + 1 history lines as StackVec<u8, 74>).
    The kernel shell's entry point (shell_main) and read_key are removed
    (console-input step 3); Shell::run stays, taking its input source as
    a parameter, as the reference loop for the port. src/shell has no
    caller until this lands, then goes.
    Prerequisite: the user heap item above (heap syscall + ease-ulib
    #[global_allocator]), so user programs can use alloc's Vec/String.
    Then port line_editor and vt_parse (and their tests) to ease-ulib
    or ease-user, swapping StackVec for Vec, and rebuild Shell::run's
    loop on READ/WRITE (its framebuffer redraw, direct UART echo and
    direct fs calls become syscalls). vt_parse's escape parsing
    pairs with console-input step 4 (special keys as ESC sequences).
    Also needs a timed read for vt_parse: a bare Esc (and the second
    Esc of Esc Esc, clear line) is only recognised by
    EscapeParser::timeout() when no byte follows soon after the ESC.
    READ blocks with no limit, so the user-space reader needs a READ
    with a timeout (or a non-blocking READ plus a sleep); without it,
    Esc only registers when the next key is pressed. The queues don't
    store timing: an arrow's ESC [ A is pushed in one go, a bare ESC
    alone, so the gap is real time at the reader. Known limitation,
    as in real terminals: if the reader falls behind and keys pile up,
    a typed Esc, [, A reads as Up.

[ ] Board role table in board.rs, once a second board makes it pay off.
    - board.rs stays data only: its own small enum of the devices the board
      has (do not import driver types; drivers depend on board, not the
      reverse), plus consts assigning roles: console input, console output,
      debug output.
    - QEMU: console in = UART + virtio keyboard; console out = UART (later
      + display); debug out = UART.
    - RP2350: console in = UART (probe) + SPI keyboard; console out =
      display + UART; debug out = UART.
    - The kernel console layer reads the table at init and registers
      sources/sinks per role; const tables let the match compile away.
    - Debug is output-only for now (STDERR convention). Debug input only
      if a kernel debug monitor is ever wanted: a one-line table change.
    - Console output gets the same role treatment as input (STDOUT ->
      console output -> UART/display/RTT sinks).

[ ] RTT (SEGGER Real-Time Transfer) as another console device, for early
    RP2350 bring-up before the UART works. Fits the role table as one more
    device; nothing above the console layer changes.
    - Input has no interrupt: poll the RTT down buffer (timer tick or a
      small periodic thread, deferrable), and on new bytes call "notify
      console input". The down buffer is already a ring, so the
      console-input struct reads it directly; no extra ring.
    - Output: the RTT up buffer is a console-output sink. Non-blocking:
      when no probe is reading and it fills, drop and count (the existing
      print policy). Never block waiting for a debugger.
    - Hardware: control block ("SEGGER RTT" magic) must sit in RAM the
      probe scans (linker placement); publish indices after data (same
      ordering discipline as the SPSC queue).
    - QEMU testing: a test plays the probe (writes the down buffer, reads
      the up buffer) and checks READ end to end. Optional interactive
      "probe": QEMU RAM backed by a shared memory-backend-file (share=on),
      a host script mmaps it and scans for the control block. Avoid the
      gdbstub (halts the VM per access).

[ ] Separate .rodata from .text (linker scripts + PMP), so read-only data
    is R only, not R+X. Hardening: today constant data is executable.
    Current state:
      - User blobs: ease-user/user-memory-qemu.x puts .rodata/.srodata
        inside the user .text output section, and usermem Role::Text
        grants R|X over the whole window.
      - Kernel: memory-qemu.x already has separate .text and .rodata
        output sections, but both sit back to back in FLASH; check what
        the flash PMP grant (pmp.rs, "kernel/user code grant") covers.
    To do:
      - Linker: give .rodata its own aligned output section (and start/end
        symbols) in both scripts; add linker ASSERTs for alignment/size as
        done for the scratch .text.
      - PMP: a Role (e.g. Rodata) with R only, plus its Backing.
      - Budget: 8 PMP entries, 2 taken by the kernel scratch .text guards,
        6 left for U-mode. A separate rodata region costs one more entry
        per process; NAPOT needs power-of-two size and alignment (padding
        cost), TOR needs two entries. Decide which before splitting.
        RP2350 is NAPOT only, so the budget is settled by the process
        memory layout item below (rodata is its entry 2).
      - Tests: a U-mode probe that jumps into its own .rodata must
        fault-kill the process; one that reads .rodata must still work.

[ ] Process memory layout for the ELF loader: fit the U-mode regions in
    the 6 PMP entries left after the kernel's 2, NAPOT only (RP2350 has
    no TOR). Do it with the move to an ELF loader, which is when each
    program's segments get placed per process instead of at the shared
    fixed link addresses.
    PMP only sees address ranges and permissions, not roles, so regions
    with the same permissions and the same backing can share an entry,
    as long as every thread of the process should see them.
    Budget:
      1. Text                  R+X  fixed (flash/blob)
      2. Rodata                R    fixed (see .rodata item above)
      3. Data + bss            R+W  one NAPOT block, shared by the
                                    process's threads
      4. Stack                 R+W  this thread's own, swapped on context
                                    switch (as today: usermem::to_pmp)
      5. Heap                  R+W  only if the program asks (user heap
                                    item): created after spawn, so it
                                    can't join entry 3's block
      6. BufRW                 R+W  PSRAM
      (BufR, R only, PSRAM: no entry left; add when something needs a
      read-only buffer, e.g. by sharing with a program that has no heap)
    Notes:
      - Heap is per process (threads share it); stacks are per thread,
        up to MAX_THREADS_PER_PROC. Keeping the stack in its own swapped
        slot means every thread's stack is its own NAPOT region: an
        overflow off either edge PMP faults immediately, for every
        thread, and a thread can't reach its siblings' stacks at all.
        A stack inside the shared block would lose both. This is the
        realistic failure in Rust (deep recursion, big locals) and safe
        Rust has no other guard; the user stack canaries are a second
        line.
      - No spare entry. A heap merged into entry 3's block would have
        saved one (merged costs next_pow2(data + bss + heap), the
        padding becoming heap), but the heap is on demand to save
        memory for programs that don't need one, so it can't be sized
        at spawn. Revisit if the ELF loader lets a program declare its
        heap size in the image (cf. Windows PE heap fields).
      - Growing the heap: with no MMU, allocations can't move, and a
        bigger NAPOT region must be aligned to its new size, so growing
        in place rarely works.
      - No BufW: R=0, W=1 is a reserved PMP encoding. Write access is
        always R+W.
      - BufRW/BufR live in PSRAM, different physical memory, so they can
        never share the RW block's entry.
      - Heap as its own NAPOT region: an overrun off either end faults.
        Not caught: one heap allocation into the next (unsafe code only).
    Today: Data and Bss are Backing::Fixed (__user_data_start,
    __user_bss_start), Stack and Heap are separate UserPd0 allocations,
    one entry per Role (usermem.rs). Open question: how data/bss get
    into the block without an MMU (link each program for its block,
    position-independent code, or relocations applied by the loader).
    The heap itself is designed in the user heap item.

[ ] Raw key events for games (Doom): press, release and hold for every
    key, including modifiers and arrows, so a game knows what is held.
    The console stream can't carry this: the Decoder drops releases,
    folds modifiers into characters and filters repeats, so DecodedKey
    and console bytes are both cooked.
      - Branch before the Decoder: keystroke_decode (virtio keyboard
        service thread) pushes each input::Event to a raw queue of
        fixed-size event records, as well as feeding the Decoder.
      - Its own fd/device for the game to read; console fd 0 unchanged.
      - Focus rule: while a game holds the raw stream, the cooked path
        stays quiet, or keys pressed in the game also reach the shell.
      - Keyboard only: the UART (terminal bytes, no releases) can't take
        part. The RP2350 SPI keyboard driver should produce the same raw
        events, so the game never sees which keyboard it is.
