    Yes — the idiomatic Rust answer is an RAII guard: convert "I must remember to restore
    interrupts" from a manual responsibility into a typestate that does it automatically
    when dropped.

    The pattern: introduce a small IrqGuard struct in arch. Make disable_interrupts()
    return one. The guard stores the previous interrupt state and its Drop impl calls
    restore_interrupts(prev). You already use this pattern — your IrqSpinLock returns a
    lock guard whose Drop releases the lock. Same idea, applied to interrupts directly.

    Why this solves your refactor: once interrupt restoration is handled by Drop, neither
    function has to think about it from inside the shared body. reschedule constructs the
    guard at its top; preempt doesn't. The shared inner helper can early-return freely —
    Rust's drop semantics ensure the guard runs only in the function that built it, on
    every path out (early return, normal return, even panic).

    So the refactor becomes:
    - Extract the lock/wake/get-pair/bookkeeping/switch_to/post-switch-cleanup body into a
    shared private helper on Scheduler (e.g. do_switch(new_state: PostSwitch)).
    - The helper has the early return on curr==next with no cleanup — exactly what you
    want.
    - reschedule becomes: build IrqGuard, call helper. Done.
    - preempt becomes: call helper. Done.

    One subtlety to think through before you commit: today, reschedule calls
    restore_interrupts(prev) after switch_to returns and post-switch-cleanup runs. With a
    guard, the drop happens at function exit — same place, so behavior is preserved. The
    trampoline comment ("mret has restored MIE") suggests the explicit restore is partly
    belt-and-suspenders; the guard approach keeps that safety net while removing the
    duplication. Worth tracing one resume path mentally to confirm you're happy with the
    ordering.

    the guard type next to them), then src/kernel/sched/roundrobin.rs for the extraction.

14. Two pieces: declare the region in your linker script, then tag the static.

**`memory.x`** — add the region and a section into it:

```
MEMORY {
    /* ... your existing regions ... */
    SRAM5 : ORIGIN = 0x20081000, LENGTH = 4K  /* adjust to your map */
}

SECTIONS {
    .sram5 (NOLOAD) : ALIGN(8) {
        *(.sram5 .sram5.*)
    } > SRAM5
} INSERT AFTER .bss;
```

`NOLOAD` means no bytes are stored in the flash image and the startup code won't try to copy or zero it. Perfect for audio buffers since you overwrite them anyway.

**Rust side** — pin the buffer with `#[link_section]` and use `MaybeUninit` so you don't owe anyone an initial value:

```rust
use core::cell::UnsafeCell;
use core::mem::MaybeUninit;

#[link_section = ".sram5"]
static AUDIO_BUF: UnsafeCell<MaybeUninit<[i16; 1024]>> =
    UnsafeCell::new(MaybeUninit::uninit());
```

That's it — 2KB stereo i16 buffer living in SRAM5, zero flash footprint, no startup cost.

**A couple of practical notes:**

- For ping-pong DMA, just declare two: `AUDIO_A` and `AUDIO_B`, both in `.sram5`. They'll pack into the region in declaration order.
- If you ever want an *initialized* table there (e.g. a sine LUT for a synth), drop the `NOLOAD`, write `} > SRAM5 AT > FLASH`, and your `cortex-m-rt`-style startup needs a `.sram5` copy loop. For buffers, stay with `NOLOAD` — simpler and cheaper.
- Use `addr_of_mut!(*AUDIO_BUF.get())` to hand a pointer to the DMA engine; avoid taking `&mut` references that could alias with the DMA's writes.
- Double-check your SRAM5 base address in the RP2350 datasheet against your linker map — the "4KB direct-mapped per-core" banks have specific addresses and getting them wrong silently puts the buffer in striped RAM with no warning.

  20. A more flexible pattern is caller-provided buffer (read_into):

  pub fn read_file_into(&self, entry: &DirEntry, buf: &mut [u8]) -> Result<usize, FsError>;

 23. The "proper" way to reclaim is the pivot pattern:

  1. Allocate a small dedicated idle stack from heap (say 512 B).
  2. From main(), switch sp to that new stack via asm.
  3. Call idle_thread() on the new stack.
  4. Mark the original boot stack region as available to the heap allocator.

  That requires:
  - A few lines of asm to pivot sp safely
  - Updating the bootstrap TCB's stack_base and stack region after the pivot
  - Telling your allocator about the newly-freed region

  It's ~50 lines of work and is what Linux/seL4/L4 do under the hood. The savings on your hardware are ~3 KiB of SRAM
  and ~2 KiB of PSRAM per HART.

  Honest take: for a hobby OS, not worth it. The complexity vastly exceeds the gain. 1.5 KiB allocated for boot stack
  on a system with 520 KiB SRAM + 8 MiB PSRAM is 0.02% of memory. The pivot pattern is a fun thing to implement someday
   for the educational value, but as a memory-conservation strategy it's diminishing returns.

  The shape of the wrapper:

  A PowerAware<Plic> wrapper holds three things:
  1. The inner PLIC driver (the existing Plic struct, untouched)
  2. A state field: enum PowerState { Active, Suspended }
  3. A saved-state struct containing everything needed to reconstruct PLIC hardware after wake — array of priorities
  for each interrupt source, array of enable bits per context, threshold per context. For your setup that's maybe 96
  bytes of static save area.

  The state machine:

  - Active: normal operations pass through to the inner PLIC
  - Suspended: hardware registers may be lost (PLIC is in a powered-down domain); operations either panic, queue, or
  return error depending on your policy

  Suspend method:

  Called before entering the sleep state that powers PLIC down. Steps:
  1. Read every per-source priority register into the save struct
  2. Read every per-context enable register into the save struct
  3. Read each context's threshold into the save struct
  4. Flip state to Suspended

  Resume method:

  Called after wake, before re-enabling interrupts globally. Steps:
  1. Walk save struct and write all priorities back
  2. Write enable registers back
  3. Write thresholds back
  4. Flip state to Active

  How operations interact with state:

  Two valid policies, pick one:
  - Strict: any enable_irq()/set_priority() call while Suspended panics. Forces correct kernel sequencing (suspend
  last, resume first among drivers that depend on IRQs).
  - Lazy: operations write to the save struct directly while Suspended, are flushed to hardware on resume. More
  forgiving but adds complexity.

  For PLIC specifically, strict is cleaner — IRQs are foundational, you'd never want a subsystem fiddling with them
  while the controller is dormant.

  Generalizing to a trait:

  Define a PowerManaged trait with suspend(&mut self) and resume(&mut self) methods. Each driver implements it. A
  central power manager holds a list of &mut dyn PowerManaged references and calls suspend() on each (in dependency
  order) before sleeping, then resume() in reverse order on wake. Order matters: PLIC suspends last (so other drivers
  can still acknowledge pending IRQs while shutting down) and resumes first (so other drivers' resume code can re-arm
  interrupts).

  Memory cost for PLIC wrapper specifically: ~96 bytes save area + a few bytes of state = trivial. For the full driver
  set: maybe 2-4 KB of save state plus the suspend/resume vtable.

  The hard part isn't the wrapper — it's the ordering and dependency graph. UART driver depends on PLIC for IRQs.
  Scheduler depends on timer. Display driver depends on framebuffer being in retained PSRAM. Getting suspend/resume
  order right is where bugs hide. That's the design work; the per-driver wrapper is mostly mechanical.



  1. Per-driver typestate (easy, useful): Each driver has Plic<Active> and Plic<Suspended> zero-cost markers. Methods
  only exist on appropriate states. Plic::suspend(self) -> Plic<Suspended>, Plic::resume(self) -> Plic<Active>.
  Prevents you from calling set_priority() on a suspended PLIC at compile time. This works well and is worth doing.


  Realistic recommendation for EASE:

  - Use typestate per driver (cheap, idiomatic, catches real bugs). E.g. Plic<S: PowerState>.
  - Use capability tokens for the 1-2 most critical dependencies (PLIC → everything-that-uses-IRQs). Accept the
  lifetime ceremony there because it pays off.
  - For the general N-driver suspend order, use a runtime priority field with documented ordering, and assert
  correctness at startup. A bad order panics on first boot, never reaches production.

  The type-system approach has diminishing returns. Pairwise dependencies (X needs Y) are easy and worth enforcing. A
  10-driver topological suspend chain is theoretically expressible but practically a maintenance burden — you'll spend
  more time appeasing the compiler than the bug-prevention is worth.

  One pragmatic middle ground: Define a #[derive(PowerOrder)] proc-macro (you already have ease-macros) that emits a
  const ORDER: u32 from an attribute. Then your runtime suspend loop sorts by ORDER and you get compile-time-visible
  declarations without the lifetime tax.

  Step 1: Declare per-CPU variables once

  Step 2: One template in the linker script

  /* Single TLS template, lives in flash */
  .tdata : {
      __tdata_start = .;
      *(.tdata .tdata.*)
      __tdata_end = .;
  } > FLASH

  .tbss (NOLOAD) : {
      __tbss_start = .;
      *(.tbss .tbss.*)
      __tbss_end = .;
  }

  __tls_template_size = __tbss_end - __tdata_start;

  Step 3: One slot per hart in scratch RAM

  .sram8_tls (NOLOAD) : ALIGN(8) {
      __hart0_tls = .;
      . = . + __tls_template_size;
  } > SRAM8

  .sram9_tls (NOLOAD) : ALIGN(8) {
      __hart1_tls = .;
      . = . + __tls_template_size;
  } > SRAM9

  Step 4: Boot code initializes each hart's slot

  For each hart, in early boot:

  // Copy the .tdata template (initial non-zero values) from flash
  core::ptr::copy_nonoverlapping(
      &__tdata_start as *const u8,
      my_tls_base as *mut u8,
      tdata_size,
  );
  // Zero the .tbss portion
  core::ptr::write_bytes(
      (my_tls_base + tdata_size) as *mut u8,
      0,
      tbss_size,
  );
  // Point this hart's tp at its slot
  asm!("mv tp, {}", in(reg) my_tls_base);

  Now CURRENT_TASK.get() automatically resolves to this hart's copy via tp. No per-hart linker sections, no per-hart Rust statics.

  Step 5: Adding a third hart

  SRAM10 : ORIGIN = 0x80082000, LENGTH = 0x1000

  .sram10_tls (NOLOAD) : ALIGN(8) {
      __hart2_tls = .;
      . = . + __tls_template_size;
  } > SRAM10

  That's it. No new variables, no source changes, no new .sramN_percpu sections.

  Caveats for Beginners

  1. #[thread_local] in Rust is nightly-only. In stable kernels people often use tp-relative access via small inline-asm helpers, or use a crate like riscv that abstracts it. The
  linker layout doesn't change.
  2. You still need to set tp once per hart, early. This is the same kind of one-time-per-hart work you already do for setting up the stack pointer.
  3. TLS has a "model" (local-exec, initial-exec, etc.). For a static kernel binary you always want local-exec — flip the appropriate compiler flag (-C relocation-model=static
  and/or -Z tls-model=local-exec). For a beginner: just know that the wrong model produces relocations the kernel can't resolve.
  4. tdata/tbss sizes must be known at link time. That's fine — they always are.
  5. TLS variables can't be referenced before tp is set up. So the very-early boot code can't use them; it has to fall back to mhartid reads. Trivial constraint in practice.

    28. A null-pointer guard is a small locked, no-access PMP region sitting over the lowest addresses (around address 0). Once it's in place, any
  access to a near-null address — read, write, or instruction fetch — traps immediately with a precise fault, instead of silently succeeding or
  corrupting whatever happens to live at address 0.

  Why you'd want it. A null pointer is just address 0 (recall our earlier null == 0 chat). When code dereferences a null pointer, it accesses
  address 0. Without a guard, what happens depends entirely on what's mapped there:
  - On real RP2350, address 0 is the boot ROM — mapped and readable. So a null read silently returns ROM bytes (your bug produces garbage data
  and limps on), and a null write hits ROM (ignored or faults unpredictably). Silent-wrong is the worst failure mode: the bug surfaces
  somewhere far away.
  - On QEMU virt, address 0 is likely unmapped, so a null access may already fault — meaning the guard is partly redundant in your current test
  environment, but not on the silicon you're targeting.

  The guard makes this deterministic everywhere: null access → clean fault at the instruction that did it, with mtval showing the address. That
  converts "mysterious corruption later" into "faulted right here."

  Why it's specifically an M-mode protection. This is the key thing to connect to last message's principle. In U-mode, address 0 is already
  denied — no region grants it, and U-mode default-denies unmatched addresses, so a U-mode null deref already faults. The guard adds nothing
  there. The value is entirely for M-mode (your kernel), where the default is allow: without an explicit locked deny-region, the kernel can
  freely touch address 0. So the null guard is kernel self-protection — it catches the kernel's own null derefs. And that matters because a
  kernel is full of unsafe raw-pointer code (MMIO, linker symbols, pointer arithmetic, any NonNull::new_unchecked). Safe Rust never produces a
  null deref — references are non-null and Option<&T> uses the null niche — but your unsafe blocks can, and NonNull::new_unchecked(null) is
  outright UB the optimizer may "reason around." The guard is the runtime backstop for exactly those.

  Design choices, if you built it:
  - Size: the minimum NAPOT is 32 bytes, but that only catches addresses 0–31. Real null bugs often look like null_ptr->field (address = offset
  of field) or array[i] through a null base — small offsets from null. So you'd typically cover a whole page (a 4 KB NAPOT region at 0) to
  catch null-plus-small-offset, not just exact zero. Nothing legitimate lives in [0, 0x1000), so it's free to forbid.
  - Permissions: zero R/W/X, A-field = NAPOT, L = 1 (locked, so M-mode is bound by it).
  - Placement: a low-numbered locked region, alongside your scratch-text guard (lowest-number-wins means nothing can override it — though
  nothing overlaps it anyway).

  The catch in your code (this is the real blocker, and it's the same one I flagged): your PmpCfg::set does if permissions == 0 { 0 }, which
  sets the A-field to OFF — i.e., passing zero permissions disables the region rather than making it deny-all. A null guard needs A = NAPOT
  with R=W=X=0 and L=1. So before you could build one, you'd fix set to keep the NAPOT/A bits when permissions are zero, distinguishing "region
  off" from "region matches and denies everything." That same fix is what any no-access guard (null guard, stack dead-zone) needs.

  My honest take for where you are: it's a classic, legitimate hardening technique and well worth understanding — but it's defense-in-depth,
  not a fix for a bug you have, its payoff is mostly on real hardware (QEMU likely faults on null already), and it costs you the permanent
  region plus the set rework. So it fits exactly the advice from last time: don't spend the locked region speculatively. Keep it in your back
  pocket as a strong candidate for when you harden for real silicon — at which point fixing set to express no-access regions unlocks both the
  null guard and proper stack dead-zone guards in one go.


  29.A closure is an anonymous struct + a generated call-function. When you write move || use(x, y), the compiler synthesises a hidden struct — call it AnonF { x: …, y: … } — whose
  fields are exactly the captured variables. Calling the closure is calling a compiler-generated FnOnce::call_once(self: AnonF) that runs the body, reading self.x, self.y. So a
  closure value is just those captured bytes laid out as a struct, and "invoking" it is "hand that struct to its call-function." That's the whole trick: storing the closure =
  storing that struct's bytes; presenting it to you = giving the trampoline a *mut F and letting it call F's call-once.

  The stack layout. The stack grows downward (high → low address). You forge the initial frame from the top down, placing the closure first (highest), then the register-restore
  frame below it:

   high addr
   ┌───────────────────────────┐ ← stack_region.top()
   │  closure F (captured env)  │   ptr::write the moved-in closure here
   ├───────────────────────────┤ ← closure_addr (aligned to align_of::<F>())
   │  forged register frame:    │   the bytes your switch-in code restores
   │    ra = run_closure_thread │     ← entry PC: where the thread "returns" to
   │    a0 = closure_addr        │     ← first arg: pointer to the closure
   │    s0..s11 = 0 (callee-saved)│
   ├───────────────────────────┤ ← sp  (16-byte aligned)
   │      ... free stack ...     │
   └───────────────────────────┘ ← stack_region.base()  (canary lives here)
    low addr

  The relationship you asked about: sp does not point at the closure. sp points at the bottom of the register frame — the thing your context-switch restore pops when it first
  schedules the thread. The closure sits above that frame. The link between them is one register slot: the forged a0 (RISC-V's first-argument register) holds closure_addr. So sp →
  frame, and frame → (via a0) → closure.

  How it "presents the struct to you": your trampoline is run_closure_thread::<F>(closure_ptr: *mut F). When the switch restores the frame and the thread starts executing at the
  forged ra (= run_closure_thread::<F>), the calling convention says the first parameter arrives in a0. Since you forged a0 = closure_addr, the function's closure_ptr parameter is
  the address of the on-stack closure. Inside, you core::ptr::read(closure_ptr) to move the F out of the stack slot into a local, then call it. It's monomorphised, so this exact
  instance of run_closure_thread statically knows F's size, alignment, and call-function — the stored function pointer is your "type-erased handle," and entering it re-establishes
  the type.

  Construction order (forging downward):
  1. Start at top = stack_region.top().
  2. closure_addr = align_down(top - size_of::<F>(), align_of::<F>()); ptr::write(closure_addr as *mut F, entry) — this moves the closure onto the stack.
  3. Build the register frame below it, setting ra = run_closure_thread::<F> and a0 = closure_addr.
  4. Round sp down to a 16-byte boundary (RISC-V ABI requires sp 16-aligned at function entry) and store it in the TCB.

  Two alignments to respect independently: the closure slot needs align_of::<F>(), and sp needs 16.

  Notice the payoff: the TCB needs no closure field at all — sp plus the closure-address-baked-into-the-frame is the entire mechanism. No Box, no into_raw, no separate pointer.

  One Drop subtlety, connecting to our leak discussion. Step 2 moves F into raw stack bytes via ptr::write. If spawn then hits an early-exit (no slot) and you just drop
  stack_region, the memory is freed but F's destructor never runs — if the closure captured something with Drop, you leak it, exactly like the Box case. The clean fix is the same
  "commit last" move: do the ptr::write of the closure after the slot is secured, so on any failure path entry is still a normal owned local that drops naturally — no manual undo.
  If you must forge before the slot check, the undo is ptr::drop_in_place(closure_addr as *mut F) before freeing the stack. Same lesson, new setting: keep the irreversible move
  (into_raw then, ptr::write now) as the final committing step.

  On the trampoline side, after f() returns the thread is done, so it tail-calls your thread-exit path. The closure slot up top is just stack space now — it gets reused as the
  thread runs, no cleanup needed, because ptr::read already moved ownership into f and call_once consumed it.

30.
The real bugs (all verified against the source, with the strongest first)

1. Test suite is red right now. debug_assert!(cluster > 2) at fs/bpb.rs:140 — cluster 2 is the first valid FAT16 data cluster (the code's own docs say so). I reproduced the failure: 158/159 host tests pass. Since debug assertions are on in the QEMU test profile too, and HELLO.TXT sits at cluster 2 on the disk image, the QEMU FS tests should hit it as well. The assert evidently landed without a full ci.sh run.
2. Mutex can admit two owners. Mutex::lock blocks itself, drops the lock, then parks with interrupts enabled in between (mutex.rs:125-127). A timer preemption in that window clobbers Blocked→Ready (stride.rs:137, stride.rs:642), the thread resumes, and lock() returns a guard the holder never released. Completion survives the same window only because it re-checks in a loop; Mutex doesn't.
3. Kernel runs on a user-controlled stack pointer. On the scheduled user-thread exit path, the trap epilogue skips the mscratch restore for M-mode returns, so sched::exit() executes in M-mode with sp = whatever the user thread last set (arch/trap.rs:130-151). Security-critical class of bug, currently cushioned only by user-mode being explicitly WIP (user threads also run non-preemptible, arch/usermode.rs:44-47).
4. Soundness hole in SpscRingBuf (spsc.rs:20): unsafe impl Sync requires only T: Copy, not T: Send, and nothing enforces the single-producer/single-consumer discipline — a data race is reachable from safe code. The atomics orderings themselves are correct and Miri-tested.
5. Any println! over 256 bytes deadlocks. The buffered UART path spins waiting for a drain interrupt while holding an IrqSpinLock that masks that interrupt (uart.rs:31-73).
6. FAT16 treats the disk as trusted. No cluster-chain validation anywhere: cycles mean infinite loops; delete_file can follow a crosslinked chain to cluster 0 and clobber the FAT media descriptor (volume.rs:266-274); non-UTF-8 filenames (legal in 8.3) panic the kernel from ls (dir_entry.rs:57-62). Also read_at is unfinished — ignores its offset, never fills the caller's buffer, returns Ok (volume.rs:151-186).
7. Smaller but real: wrong index in clear_wakeup_signal(process_idx) clears an unrelated thread's wakeup bit (process.rs:83); classic seqlock reader-fence miss in CounterU64::get (counteru64.rs:60-63); IrqSpinLock::try_lock leaks a ticket and would wedge the lock forever if the currently-dead code were ever used (spinlock.rs:67-88); spawning a second user process zeroes the first one's .bss (usermemmap.rs:166-172).

Systemic patterns (more telling than any single bug)

- The safety comments are weaker than the code. The percpu other_* accessors carry copy-pasted safety justifications asserting the opposite of what the functions do (percpu.rs:78-122); Buddy::dealloc is unsafe with no contract at all; several comments describe already-fixed bugs or nonexistent fields. In a codebase this unsafe-heavy, unreliable safety comments are a maintenance risk in themselves.
- Dead code is accumulating behind a blanket -A dead-code in ci.sh — originally for the reference allocators, now also masking fat16.rs (138 lines, entirely unreachable), the never-called mount(), and the broken read_at.
- The test suite has been widened around a known defect rather than the defect fixed: nine assertions carry RESIDUAL-TAIL markers loosening wake-latency bounds to 110–220ms, so the suite can't see regressions in exactly the property the author cares most about.
- Docs are bimodal. In-source documentation (FAT16 diagrams, linker script, scheduler rationale) is teaching-quality; the top-level docs are stale (ARCHITECTURE.md describes modules that don't exist, README is one line) and there's committed LLM-conversation residue in comments (fs/mod.rs:115, stride.rs:519). Also, nothing in the tree supplies --target/linker args — .cargo/config.toml appears to be missing or untracked, so a fresh clone can't build the kernel.
